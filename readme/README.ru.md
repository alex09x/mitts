Mitts самостоятельно планирует воркспейс и вызывает `rustc` напрямую. Каждое
действие компиляции получает ключ, полученный из всех его входных данных. Результат сохраняется
один раз в общесистемном неизменяемом хранилище и восстанавливается в каждый воркспейс,
которому он необходим, между проектами, worktree и ветками.

Если входные данные не могут быть учтены, действие пересобирается, а не угадывается.

## Проблема

Кэш сборки Cargo находится в каталоге `target/` каждого воркспейса. Все,
что создает новый `target/`, начинает с нуля:

- второй чекаут или `git worktree` того же репозитория,
- переключение на ветку, изменяющую `Cargo.lock`, с последующим переключением обратно,
- другой проект, зависящий от тех же крейтов с теми же фичами,
- параллельные агенты разработки, каждый из которых работает в собственном worktree.

Один и тот же `serde`, `syn` или `tokio` компилируется снова и снова, и каждая копия
занимает место на диске.

Обычные обходные пути имеют существенные недостатки:

- **Общий `CARGO_TARGET_DIR`** сериализует сборки за одной блокировкой, а
  проекты с разными наборами фичей перезаписывают артефакты друг друга.
- **Обертка компилятора, такая как sccache**, видит по одному вызову `rustc` за раз. Ее
  ключ зависит от абсолютных путей, если они не нормализованы, а крейты,
  вызывающие линковщик (`bin`, `proc-macro`, `dylib`), не кэшируются. Cargo по-прежнему
  планирует сборку и запускает каждый build-скрипт.

Mitts идет другим путем: он заменяет исполнитель Cargo, а не компилятор.
Он видит весь граф единиц компиляции, поэтому может вычислять ключ каждой единицы на основе ключей ее зависимостей,
кэшировать единицы компоновки и выполнения build-скриптов, а также позволять нескольким сборкам безопасно
разделять одно хранилище.

## Основные возможности

- **Повторное использование между воркспейсами.** Одно хранилище на машину. Зависимость, скомпилированная для
  одного чекаута, восстанавливается в следующий с теми же входными данными.
- **Полные ключи.** Тулчейн, таргет, профиль, флаги, фичи,
  содержимое исходников, ключи зависимостей и отслеживаемое окружение. Неизвестные входные данные означают
  пересборку.
- **Манифесты Cargo остаются контрактом.** Никаких новых манифестов, никакого второго локфайла.
  Процессы сборки, тестирования, линтинга, покрытия и формирования архива исходников для релиза в этом репозитории работают
  через Mitts; они не вызывают CLI Cargo. Внешняя совместимость с Cargo
  остается доступной для пользователей.
- **Единицы компоновки и build-скрипты кэшируются.** Исполняемые файлы, тесты, proc-макросы
  и выполнения build-скриптов получают ключи и сохраняются, а не только `rlib`.
- **Параллельные сборки взаимодействуют.** Блокировки на уровне ключей: два терминала или worktree,
  которым требуется одна и та же зависимость, компилируют ее один раз. Один jobserver ограничивает
  параллелизм для всех процессов Mitts на машине.
- **Безопасное совместное использование.** Объекты хранилища неизменяемы: публикуются атомарно, хранятся
  только для чтения и восстанавливаются через reflink или копирование. `MITTS_VERIFY_RESTORE=1` повторно вычисляет хэш каждого
  объекта перед его восстановлением (по умолчанию хранилищу оказывается доверие, что экономит одно чтение
  каждого восстанавливаемого байта). Если файловая система не поддерживает reflink, восстановление создает жесткую ссылку (hardlink)
  объекта хранилища, доступного только для чтения, в `target/` вместо копирования его байтов: разделяемый inode
  сохраняет права `0o444` (`0o555` для исполняемых файлов), индекс целевого каталога отклоняет ссылку, получившую
  биты записи, а Mitts заменяет файлы воркспейса исключительно путем переименования. Никаких доступных для записи
  ссылок на объекты хранилища. `MITTS_STORE_HARDLINKS=0` сохраняет приватные копии для воркспейсов,
  в которые другие инструменты пишут на месте.
- **Подготовка воркспейса без копирования.** Внутриворкспейсные псевдонимы библиотек, вторичные исполняемые файлы
  и атомарная подготовка единиц используют жесткие ссылки внутри воркспейса и продвижение переименованием без
  копирования байтов. Когда `MITTS_CACHE_DIR` и `target/` воркспейса находятся на одном и том же
  томе файловой системы, операции продвижения работают без копирования байтов; между отдельными
  точками монтирования они прозрачно переключаются на безопасное копирование.
- **Быстрый путь при отсутствии изменений.** Неизмененный воркспейс пропускает планирование и вычисление ключей.
- **Единый CLI.** `build`, `run`, `check`, `clippy`, `fmt`, `test` (включая доктесты),
  `coverage`, `explain`, `fetch`, `gc`, `clean`.

<a id="quick-start"></a>
## Быстрый старт

Установите последний подписанный нативный релиз:

```sh
curl -fsSL https://mittsbuild.com/install.sh | sh
```

Чтобы собрать из исходного чекаута, сначала установите последний выпущенный Mitts, затем используйте
Mitts для сборки чекаута:

```sh
git clone https://github.com/alex09x/mitts
cd mitts
mitts build --release
MITTS_JOBS=2 mitts build     # limit concurrent native build units
install -m755 target/release/mitts "$HOME/.cargo/bin/mitts"
```

Затем запускайте его внутри любого воркспейса Cargo:

```sh
mitts build                  # compile into target/debug/
mitts build --release
mitts run                    # build and run a binary
mitts test                   # unit, integration and doc tests
mitts test --tests -p foo    # Cargo-style target selection
mitts test -c                # every test in its own process, all the cores (-c=8: 8): docs/test-concurrency.md
mitts test --all-targets --no-run  # compile tests, examples and benchmarks
mitts bench                  # build benchmark targets (bench profile) and run them with --bench
mitts bench --bench speed -- --save-baseline main
# The cache stays under MITTS_CACHE_MAX_BYTES (default 100G) by itself: docs/cache-limits.md
mitts llvm-cov --ignore-filename-regex 'tests/' --fail-under-lines 80
mitts check | clippy | fmt | coverage
mitts explain                # the plan, units and why each is cached or not
mitts fetch                  # prefetch dependencies into the source store
mitts package                # create and verify a source archive
mitts publish --dry-run      # prepare publication without uploading
mitts gc                     # prune the shared store within quotas
mitts clean                  # remove this workspace's Mitts artifacts
```

Для Git-проектов упаковка в настоящее время требует чистого репозитория с пакетом в его корне.
Шаблоны `include` в манифесте могут выбирать игнорируемые файлы; вложенные пакеты воркспейса
и каталоги по символическим ссылкам пока не поддерживаются. `mitts publish` нацелен на crates.io и считывает
токен из `CARGO_REGISTRY_TOKEN`.

Mitts записывает результаты сборки в стандартные каталоги Cargo `target/debug/` и `target/release/`.
`CARGO_TARGET_DIR` и `--target-dir` задают другой корневой каталог для вывода.
Его общий кэш расположен отдельно
(`--cache-dir`, иначе `$MITTS_CACHE_DIR`, иначе `$XDG_CACHE_HOME/mitts`, иначе
`~/.cache/mitts`). Хранилище артефактов, кэш действий, блокировки, jobserver, хранилище
исходников, git-зеркала и кэш индексов находятся под этим единым корнем.

Git-зависимости, публичные или приватные, клонируются самим Mitts с помощью системного
`git`, поэтому ваши SSH-ключи, ssh-agent, хелперы учетных данных и `GIT_SSH_COMMAND` применяются
точно так же, как и в командной строке; интерактивные запросы отключены, поэтому при отсутствии учетных данных
происходит ошибка вместо зависания. Ничто не проходит через Cargo. Чекаут, уже
выполненный Cargo в `~/.cargo/git/checkouts`, используется повторно вместо повторного клонирования.

Любой другой способ, которым Cargo получает крейт, работает точно так же, из той же конфигурации:

- **Альтернативные реестры**: `[registries.<name>] index = "sparse+https://…"`
  и `registry = "<name>"` у зависимости. Токены поступают от поставщиков
  учетных данных Cargo в порядке Cargo: `cargo:token` (окружение и
  `credentials.toml`), `cargo:macos-keychain`, `cargo:libsecret`,
  `cargo:token-from-stdout <command>`, а также плагины, такие как
  `cargo-credential-1password`, через протокол поставщиков учетных данных,
  настроенный параметрами `[registry] global-credential-providers`,
  `[registries.<name>] credential-provider` и `[credential-alias]`. Реестр,
  чей `config.json` указывает `auth-required`, завершается с понятным сообщением, если ни у одного
  поставщика нет токена. Реестры с git-индексом отклоняются: используйте протокол
  sparse.
- **Зеркала**: `[source.crates-io] replace-with = "<name>"` с
  `[source.<name>] registry = "sparse+https://…"`. Байты поступают из зеркала,
  `Cargo.lock` продолжает указывать crates.io, в точности так, как это записывает Cargo.
- **Вендоренные исходники**: `[source.vendored-sources] directory = "vendor"` из
  `cargo vendor`. Пакеты проверяются по их файлу `.cargo-checksum.json`
  и копируются в хранилище; ничто не обращается к сети, включая
  git-пакеты. При отсутствии локфайла каталог vendor служит индексом.
- **`[patch]`**: `[patch.crates-io] foo = { path = … }` или `{ git = … }`
  заменяет пакет реестра; при отсутствии локфайла замена
  разрешается и фиксируется, и она должна удовлетворять требованию, как и в Cargo.

Секция `[env]` в конфигурации Cargo применяется к rustc, build-скриптам и программам,
которые запускают `mitts run` и `mitts test`, с соблюдением правил Cargo `force` и `relative`;
конфигурационные файлы являются входными данными, поэтому измененное значение пересобирает то, что его прочитало.

При отсутствии `Cargo.lock` Mitts формирует его так же, как Cargo: наивысшая
неотозванная (non-yanked) версия для каждого требования, распространение фичей по ребрам графа,
включение опциональной зависимости только тогда, когда фича активирует ее, одна версия на
диапазон совместимости. В результате получается локфайл, который Cargo принимает как свой собственный.

<a id="how-it-works"></a>
## Как это работает

```
Cargo.toml + Cargo.lock
        │
        ▼
 resolve ─── reuse Cargo.lock, or resolve against the crates.io sparse index
        │
        ▼
 fetch ───── download .crate archives in parallel, verify, unpack once per machine;
        │    clone git dependencies with the system git at the locked commit
        │
        ▼
 plan ────── compilation units: lib · bin · test · build script · proc macro
        │    with features, targets and dependency edges (Cargo's resolver rules)
        ▼
 key ─────── SHA-256 over toolchain, target, profile, flags, features,
        │    source contents, dependency keys and tracked environment
        ▼
 execute ─── parallel DAG of direct rustc calls, pipelined on .rmeta
             hit  → restore from the store (reflink, read-only link or copy)
             miss → lock the key, compile, publish atomically to the store
```

Ключ единицы включает **ключи** ее зависимостей, а не их выходные байты, поэтому
изменение где-либо ниже единицы изменяет ее ключ. Build-скрипты выполняются в промежуточном
каталоге (staging directory); их директивы (`rustc-cfg`, `rustc-link-*`, `rustc-env`, …) входят
в ключ единицы, которую они настраивают, а их объявления `rerun-if-*` определяют,
когда кэшированный запуск может быть использован повторно.

После успешной сборки Mitts сохраняет снимок воркспейса. Если ничто
в нем не изменилось, следующая сборка сразу переходит к результату. Любое несовпадение приводит к возврату
к полной сборке с вычислением ключей, поэтому быстрый путь никогда не пропускает работу, которую
выполнил бы протокол.

Полный протокол — вывод ключей, блокировки, build-скрипты, быстрый путь,
структура хранилища и сборка мусора — описан в
[docs/architecture.md](../docs/architecture.md).

<a id="architecture"></a>
## Архитектура

Mitts представляет собой независимое от языка ядро с языковыми адаптерами поверх него. Ядро ничего
не знает о Cargo; адаптер Rust преобразует воркспейс Cargo в действия
с ключами.

```
                 ┌──────────────────────────────────────────────┐
  mitts CLI ───▶ │ Rust adapter                                 │
  (src/cli)      │ manifest · resolver · fetcher · features     │
                 │ planner · keys · DAG runner · build scripts  │
                 ├──────────────────────────────────────────────┤
                 │ C/C++ adapter (experimental, Mitts.toml)     │
                 └──────────────────────┬───────────────────────┘
                                        │ actions + keys
                 ┌──────────────────────▼───────────────────────┐
                 │ Core                                         │
                 │ content-addressed store · action cache       │
                 │ key locks · jobserver · fast path · GC       │
                 └──────────────────────────────────────────────┘
```

| Путь | Что там находится |
| --- | --- |
| `src/cli/` | Обработчики команд: `build`, `test`, `clippy`, `explain`, … |
| `src/adapter/rust/` | Семантика Cargo: манифесты, локфайл, sparse-индекс, разрешение фичей, планирование единиц, ключи действий, исполнитель DAG, build-скрипты, доктесты |
| `src/adapter/c/` | Экспериментальный адаптер C/C++ на том же хранилище |
| `src/core/` | Независимое от языка хранилище (`cas.rs`), кэш действий, блокировки, jobserver, быстрый путь (`build_lock*.rs`), сборщик мусора (GC), reflinks |
| `docs/` | [Протокол](../docs/architecture.md), [архитектурные решения](../docs/decisions), [сценарии](../docs/scenarios) |
| `tests/` | Интеграционные тесты, включая тесты на паритет с Cargo и инвалидацию кэша |
| `scripts/` | Инструменты бенчмаркинга и аудита |
| `fixtures/` | Минимальные проекты Rust и C, используемые тестами |

## Что инвалидирует кэш

Попадание в кэш требует совпадения каждого входного параметра ниже. Если Mitts не может видеть
входной параметр, он не использует результат повторно.

| Входной параметр | Отслеживается как |
| --- | --- |
| Тулчейн | вывод `rustc -vV` |
| Таргет и профиль | целевой triple, настройки профиля, `RUSTFLAGS` и флаги rustflags из конфигурации Cargo |
| Фичи | разрешенный набор фичей единицы (resolver 1 или 2, как в Cargo) |
| Исходники | хэши содержимого файлов пакета и каждого файла, о чтении которого сообщает rustc (`include_str!`, `include_bytes!`, модули) |
| Зависимости | ключи действий всех единиц зависимостей |
| Окружение | соответствующие настройки `CARGO_*` и `RUST_*`, а также переменные, считываемые через `env!` / `option_env!`, с явной записью `<unset>` |
| Конфигурация Cargo | файлы `.cargo/config(.toml)`, которые прочитал бы Cargo |
| Build-скрипты | их директивы, `OUT_DIR`, а также содержимое путей `rerun-if-changed` и значения переменных `rerun-if-env-changed` |

Настроенные программы `rustc-wrapper` и `rustc-workspace-wrapper` вызываются для
компиляции. Поскольку произвольная обертка может зависеть от неотслеживаемых входных данных, Mitts
отключает повторное использование кэша действий и кэша build-скриптов при активности любой из этих оберток.
Это может замедлить такие сборки.

Некоторые proc-макросы читают файлы из вашего пакета во время своего раскрытия: `sqlx` сверяет
запросы с каталогом `.sqlx/`, `askama` компилирует `templates/`, `rust-embed` и
`include_dir` встраивают целые каталоги. rustc узнает о таких чтениях только тогда,
когда макрос регистрирует их, поэтому объявляйте такие крейты в корневом `Cargo.toml`:

```toml
[workspace.metadata.mitts]          # [package.metadata.mitts] in a single crate
impure-proc-macros = ["sqlx", "askama", "rust-embed"]
```

Крейты, зависящие от указанного макроса, получают ключи по каждому файлу в их пакете
и по их абсолютному пути: отредактированный шаблон приводит к их пересборке, а другой
чекаут никогда не использует их повторно. Любой другой макрос считается чистым (pure), а зависящие
от него единицы разделяются между worktree. Указывайте крейт, от которого вы зависите;
крейт макроса, который он подтягивает (`sqlx-macros`), тоже работает.

## Сравнение

Качественное сравнение того, как каждый инструмент повторно использует проделанную работу. Это не
заявление о производительности.

| | Cargo | Cargo + sccache | Mitts |
| --- | --- | --- | --- |
| Читает `Cargo.toml` / `Cargo.lock` как есть | да | да | да |
| Повторное использование между воркспейсами и worktree | нет (на `target/`) | да, на каждый вызов `rustc` | да, на единицу компиляции |
| Ключ зависит от пути чекаута | — | да, если не нормализован | нет для крейтов реестра; для крейтов воркспейса только если они не подходят под условия |
| Кэширует единицы `bin`, тестов и `proc-macro` | — | нет | да |
| Кэширует запуски build-скриптов | нет | нет | да |
| Одновременная сборка одной зависимости | ожидание на блокировке `target/` | оба могут компилировать при промахе | один компилирует, второй использует повторно |
| Удаленный / командный кэш | нет | да (S3, GCS, Redis, …) | планируется |
| Windows | да | да | нет |

Bazel и Buck2 решают более масштабную задачу — герметичные многоязычные сборки с
удаленным выполнением, — но требуют собственных файлов сборки вместо `Cargo.toml`.

<a id="limitations"></a>
## Ограничения

Mitts находится в статусе предварительного релиза (pre-release). Учитывайте следующее, прежде чем полагаться на него:

- **Только Linux и macOS.** Блокировки и jobserver реализованы по стандартам POSIX.
- **Только хост-таргет.** Кросс-компиляция пока не поддерживается.
- **Пока нет удаленного кэша.** Хранилище создается на каждую машину.
- **Только sparse-реестры.** Реестры с git-индексом (`registry+…`,
  отличные от crates.io, или `[source] registry = "https://…"` без
  `sparse+`) и источники `local-registry` отклоняются с выводом рекомендаций.
- **Учетные данные только читаются, никогда не записываются.** `cargo login` остается задачей Cargo;
  `cargo:wincred` поддерживается только на Windows и пропускается.
- **Некоторые единицы никогда не кэшируются:** крейты типов `cdylib`, `dylib` или
  `staticlib`, а также крейты, чьи чтения `env!` невозможно отследить. Они собираются
  всегда; о них сообщает `mitts explain`.
- **Крейты воркспейса между чекаутами.** Ваши собственные крейты используются повторно между
  worktree только тогда, когда их ключ можно сделать независимым от пути (нет
  чтений `CARGO_MANIFEST_DIR`, нет build-скрипта, нет объявленных нечистых proc-макросов).
  В противном случае ключ включает абсолютный путь. На macOS отладочные символы линковщика (debug stabs)
  записываются относительно воркспейса (`-oso_prefix`), поэтому скомпонованные
  бинарные файлы также разделяются; запускайте отладчик в корне воркспейса, чтобы
  он мог найти объектные файлы.
- **Макросы, читающие ваши файлы, объявляются вами.** Proc-макрос считается
  чистым, если проект не указывает его в списке (см. выше). Крейты, зависящие от объявленного макроса,
  отслеживают каждый файл в своем пакете; необъявленный макрос, который читает файл
  без регистрации его в rustc, может привести к устаревшему результату — в точности как
  в Cargo.
- **Build-скрипты не изолированы в песочнице (sandbox).** Скрипт, который читает файлы или переменные,
  не объявленные через `rerun-if-*`, может привести к устаревшему результату — в точности как в
  Cargo.
- **Неподдерживаемые возможности Cargo завершаются с явной ошибкой.** Например `--profile`, маски путей
  с подстановочными знаками в промежуточных каталогах в `workspace.members`. Mitts
  сообщает о них вместо угадывания.
- **Zero-copy в пределах одной файловой системы.** Продвижение единиц из промежуточного каталога (staging) без копирования требует,
  чтобы `MITTS_CACHE_DIR` и каталог `target/` воркспейса находились на одной
  файловой системе. При пересечении границ файловых систем происходит безопасный переход к стандартному копированию.

**Пока не используйте Mitts**, если вам нужны Windows, кросс-компиляция, командный кэш или
стабильный релиз. В этих случаях надежным выбором остается Cargo, опционально со sccache.

<a id="performance"></a>
## Производительность

Измерено на Mitts `0.3.17` на корпусе из **100 проектов на Rust с открытым исходным кодом** на macOS (Apple M2 Ultra, APFS) и Linux ARM64 (XFS), а также **90** на Linux x86_64 (AMD Ryzen 9 9950X, XFS) в сравнении с чистым `cargo` и связкой `cargo` со `sccache` (`0.17.0`). Каждое значение — медиана по 3 прогонам с проверкой паритета по диагностике, кодам выхода и результатам тестов; все измеренные проекты остаются в общих итогах (`0`, `7` и `0` прогонов с пометкой шума), и ни одно число не завышает результат измерений: показатели базовых линий усекаются вниз, а значения Mitts округляются вверх ([ROADMAP M8](../ROADMAP.md)). Полное исследование, данные по каждому проекту и методология опубликованы на [mittsbuild.com/the-hundred](https://mittsbuild.com/the-hundred/).

- **Воспроизведение 10 коммитов** (нет на графике): паритетное распределение — Mitts первый на 58 из 100 проектов на macOS при близких медианах (**5.6 s** с `cargo`, **5.8 s** с Mitts).

## Часто задаваемые вопросы (FAQ)

**Заменяет ли Mitts Cargo?**
Mitts читает существующие манифесты и локфайлы Cargo и обеспечивает рабочий
процесс сборки и тестирования Rust для этого проекта. Его собственные процессы CI и релизов используют Mitts
без вызова Cargo. Cargo остается доступным для внешних пользователей, которым он необходим.

**Могу ли я использовать его в CI?**
Да. CI этого репозитория устанавливает последний стабильный Mitts, затем использует его для
нативных сборок, тестов, покрытия кода, форматирования и Clippy. Общее хранилище артефактов
является локальным для каждого раннера; межмашинный удаленный кэш пока недоступен.

**Будет ли он конфликтовать с rust-analyzer или существующими результатами Cargo?**
Mitts использует те же стандартные пути вывода, что и Cargo. Его общее хранилище артефактов остается
отдельным, а `mitts clean` удаляет только проиндексированные выходные данные Mitts, которые все еще соответствуют
их записанному содержимому; он сохраняет несвязанные или замененные файлы Cargo.
Если Cargo удерживает блокировку каталога сборки профиля, очистка пропускается, пока эта
сборка не завершится.

**Где находится кэш и как его очистить?**
Параметр `--cache-dir`, иначе `$MITTS_CACHE_DIR`, `$XDG_CACHE_HOME/mitts` или
`~/.cache/mitts`; все, что кэширует Mitts, находится под этим единым корнем. Используйте
`mitts gc` для очистки в пределах квот; удаление каталога также безопасно, когда
сборка не выполняется.

**Почему единица не была закэширована?**
Запустите `mitts explain`. Команда выведет список всех единиц и причину, по которой каждая
подходит или не подходит для кэширования.

## Правила проектирования

- Поддерживать оркестрацию сборки и кэширования независимой от языка. Языковая семантика находится
  в адаптерах; Rust — первый из них.
- Для попадания в кэш требуются полные, отслеживаемые входные данные. Неизвестные входные данные считаются
  изменившимися.
- Общие артефакты неизменяемы и проверяются перед использованием. Изменяемое состояние остается
  в каждом воркспейсе. Никаких жестких ссылок на доступные для записи файлы, никаких манипуляций со временем изменения файлов.
- Очистка никогда не затрагивает артефакты активной сборки.

Правила для участников и агентов: [AGENTS.md](../AGENTS.md).
